# Steam 账号管理器（本地版 v2）

一个只在你电脑上运行的 Steam 多账号管理器。

> **★ 刚把代码下载下来？先看 [`首次使用说明.md`](首次使用说明.md) ★**
>
> 那份是从零到跑起来的保姆级步骤：装什么、点哪里、怎么确认每一步成了、卡住怎么办。
> 下面这份讲的是**它做了什么、为什么这么做**，适合跑通之后再读。

核心是一条**三态流水线**：账号添加后在「可用」，点开始使用进「使用中」并倒计时，
倒计时归零自动进「待改密」，改完密码（AI 或手动）自动回到「可用」。

```
   ┌──────────────────────────────────────────────────────────┐
   │                                                          │
   ▼                                                          │
可用 ──点「开始使用」──▶ 使用中 ──倒计时归零──▶ 待改密 ──改密完成──┘
                                              （AI 或手动）
```

**只有一个计时器**：添加账号时填的「使用时间」就是这次使用的倒计时长度。
倒计时一结束就直接进入「待改密」，不存在「使用时长」和「改密阈值」两套时间。

## 一、怎么启动

**双击 `启动.bat`**（或 `start.bat`）。

启动器会自动：检查依赖 → 构建界面 → 启动本地服务 → 打开浏览器。
界面在 `http://127.0.0.1:8787`，只监听本机，局域网和外网都访问不到。

> 首次运行需要 Node.js 22 或更高版本。没装的话启动器会提示你去
> <https://nodejs.org/> 下载 LTS 版，装完再双击一次即可。

关闭服务：在黑色命令行窗口按 `Ctrl + C`，或直接关掉窗口。

### 手动命令

```bash
npm install                 # 安装依赖
npm run build               # 构建界面
npm start                   # 启动服务
node scripts/selftest.mjs   # 后端自检
node scripts/test-mail.mjs  # 邮箱功能测试（用模拟微软服务端，不需要真 token）
```

## 二、三个界面

顶部导航栏有三个标签，**点击切换，也可以左右滑动切换**（鼠标拖拽、触控板横滑、手机触摸都支持）。

| 界面 | 什么账号在这里 | 卡片上做什么 |
| --- | --- | --- |
| **可用** | 没被使用的账号 | 点「开始使用」→ 进入「使用中」并开始倒计时 |
| **使用中** | 正在倒计时的账号 | 显示实时剩余时间；可「提前结束」放回可用 |
| **待改密** | 使用时间已用完的账号 | 「手动改密」或交给 AI；改完自动回到「可用」 |

每个界面的计数实时显示在标签上，使用中和待改密会有呼吸圆点提示。

### 一级导航（同一栏，含「添加账号」和附加界面）

需求要的是「一级界面：可用 / 使用中 / 待改密 / 添加账号 / …（用于存放多个附加界面）」，
所以这一栏里放了三组东西，**各自独立位置、互不遮挡**：

```
[ 可用 3 | ● 使用中 1 | ● 待改密 1 ]   [ ＋ 添加账号 ]   [ 更多 ▾ ]
        状态界面（点击/滑动切换）          动作入口        附加界面
```

「更多」里列出全部附加界面（批量导入 / 今日使用记录 / 邮箱 / 导出 / 设置）。
**加一个新界面只要在 `web/src/lib/store.js` 的 `ATTACHED_SCREENS` 里加一行**，
导航栏会自动多出来 —— 原来导航列数是写死的 3，加界面要同时改三个文件。

### 今日使用次数（两个口径都给）

需求原文是「今日使用账号次数（自动修改密码或手动修改密码并返回密码表单的次数）」，
而界面上另一个地方又要「今天用了第几个账号」。这是**两个不同口径**，所以两个数都显示：

| 显示 | 含义 |
| --- | --- |
| 今日已用 N | 今天点了几次「开始使用」（含点了又提前结束的） |
| 已改密 M | 今天**真正改完**几次密码（自动 + 手动，都带着新密码） |

`GET /api/stats/today` 里对应 `count` / `changes`，`/api/board` 的 `stats` 里是
`todaySessions` / `todayChanges`。

### 批量导入格式

顶栏「批量导入」（或导航栏「更多 → 批量导入」）里，一行一个账号，支持这几种写法：

```
账号--密码--邮箱--游戏名          ← 需求里给的格式，四段
steam_a--Pw1--a@icloud.com--Counter-Strike 2
steam_b--Pw2                      ← 只给账号密码也行
steam_c--Pw3--Dota 2              ← 第 3 段不带 @ 就当游戏名

账号：steam_d                      ← 标签式（多行一条记录）
密码：Pw4
游戏：Apex Legends
使用时间：6小时
备注：排位号
```

第 3 段按**有没有 `@`** 判断是邮箱还是游戏名；第 4 段是游戏名。
分隔符兼容 `--` / `----` / `——` / 逗号 / 分号 / Tab。

### 完整流程

1. **添加账号**：填 账号、密码、**使用时间**、备注、游戏名 → 立刻出现在「可用」
   （不需要刷新页面；界面上还会告诉你这是今天第几个使用的账号）
2. **开始使用**：点卡片上的「开始使用」→ 账号移到「使用中」，弹出凭据卡片
   （`账号：` / `密码：` 格式，可一键复制；顶部提示「这是今天第 N 个使用的账号」）
3. **倒计时归零**：服务端每 5 秒扫描一次，到时自动把账号移到「待改密」，
   同时创建一个改密任务并推送 Webhook
4. **改密**：
   - **AI 改密** —— 你的程序调接口拉走任务，改完回传新密码
   - **手动改密** —— 卡片上点「手动改密」，去 Steam 改完把新密码填回来
   - 也可以「跳过改密，直接放回可用」（保留原密码）
5. **回到可用**：改密完成后账号自动回到「可用」，使用时长清零，可以再次开始使用

## 三、给你的 8 条修改

| 你的要求 | 实现 |
| --- | --- |
| ① AI 帮忙改「待改密」的密码，改完放进「可用」 | `/api/automation/*` 接口，AI 回传新密码后服务端**同一事务内**把状态置回 available；「待改密」界面顶部有完整的接口指引卡片 |
| ② 使用时间在添加账号时填，不是全局设置 | 表单字段「使用时间」（分钟/小时/天 + 快捷预设），每个账号独立；设置里已彻底移除统一时长 |
| ③ 删掉「未使用过」和「已停用」 | 字段、接口、筛选、界面全部移除（老数据库的残留列不影响使用） |
| ④ 生成的密码格式 | **10~12 位随机，以字母开头**，只含数字与大小写字母，三类各至少出现一次；用**拒绝采样**保证分布均匀，不做「先塞三类再补齐」那种会抬高数字占比的写法 |
| ⑤ 添加后立刻可视化 | 创建成功后**乐观插入**本地列表 + 后台对齐服务端，实测 66ms 内出现；同时修掉了"写操作中途被自动锁库导致列表刷不出来"的根因 |
| ⑥ 三种状态的归属 | 状态直接存在 `accounts.state` 字段，由服务端唯一裁决，接口按状态查询，同一账号不可能出现在两个界面 |
| ⑦ 一个计时器，不是两个 | `usage_minutes` 就是倒计时长度；调度器只做一件事——倒计时归零 → 待改密 |
| ⑧ 三者逻辑关系 | 见上面的流程图和第二节，服务端有自愈逻辑（状态与会话不一致时自动纠正） |

## 四、AI 自动化改密接口

所有接口需要请求头 `X-API-Key: <你的 API Key>`
（在「待改密」界面的指引卡片里可以看到、复制；设置页可重置）。

完整说明：`GET /api/automation/spec`
（也可以直接在浏览器打开 `http://127.0.0.1:8787/api/automation` 看说明页）

> **已经给你写好一个可用的 worker 了** —— 见 [`worker/`](worker/README.md)。
> 它轮询这里的任务、用浏览器自动完成 Steam 改密、再回传新密码，账号自动回到「可用」。
> 装好依赖、填上 API Key 就能跑；想换成 LLM 方案，那里也写清了改哪里。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/automation/available` | 列出空闲账号（可 `?q=` 搜索），不改任何状态 |
| POST | `/api/automation/accounts/{id}/use` | **让空闲账号进入「使用中」并直接返回 账号/密码** |
| GET | `/api/automation/accounts/{id}/credential?format=text` | 只取凭据文本（`账号：\n…\n\n密码：\n…`） |
| GET | `/api/automation/tasks?status=pending` | 拉取待改密任务 |
| GET | `/api/automation/context/{id}` | 读取账号、**当前密码**、邮箱、游戏名、操作步骤 |
| POST | `/api/automation/tasks/{id}/claim` | 声明接管，body `{"worker":"my-agent"}` |
| POST | `/api/automation/tasks/{id}/progress` | 上报进度，body `{"message":"等待验证码"}` |
| POST | `/api/automation/tasks/{id}/complete` | 回传新密码 → **账号自动回到「可用」** |
| POST | `/api/automation/tasks/{id}/fail` | 上报失败，`retry:true` 可放回队列 |

前三个是给**外部程序取号用**的（对应需求里那句「空闲中账号点击使用中后输出
账号：\*\*\*\*\*\* 密码\*\*\*\*\*\*\*」）——不需要主密码，只要 `X-API-Key`：

```bash
# 看一眼有哪些空闲账号
curl -H "X-API-Key: 你的Key" http://127.0.0.1:8787/api/automation/available

# 取一个来用：账号立刻变「使用中」，返回体里直接带 账号/密码
curl -X POST -H "X-API-Key: 你的Key" \
     http://127.0.0.1:8787/api/automation/accounts/12/use
```

### 可直接运行的轮询脚本

```js
const KEY = '你的 API Key';
const BASE = 'http://127.0.0.1:8787';

while (true) {
  const { tasks } = await (await fetch(`${BASE}/api/automation/tasks?status=pending`, {
    headers: { 'X-API-Key': KEY },
  })).json();

  for (const t of tasks) {
    await fetch(`${BASE}/api/automation/tasks/${t.id}/claim`, {
      method: 'POST',
      headers: { 'X-API-Key': KEY, 'Content-Type': 'application/json' },
      body: JSON.stringify({ worker: 'my-agent' }),
    });

    // 上下文里有账号、当前密码、邮箱、游戏名
    const ctx = await (await fetch(`${BASE}/api/automation/context/${t.id}`, {
      headers: { 'X-API-Key': KEY },
    })).json();

    // ↓↓↓ 这里接你的自动化：打开 Steam 改密页 → 登录 → 取验证码 → 设新密码
    const newPassword = await yourAutomation(ctx.target);

    // 回传后账号自动从「待改密」回到「可用」
    const done = await (await fetch(`${BASE}/api/automation/tasks/${t.id}/complete`, {
      method: 'POST',
      headers: { 'X-API-Key': KEY, 'Content-Type': 'application/json' },
      body: JSON.stringify({ newPassword, worker: 'my-agent' }),
    })).json();

    console.log(done.account.username, '→', done.account.stateLabel); // → 可用
  }

  await new Promise((r) => setTimeout(r, 3000));
}
```

### Webhook 主动通知

在设置页填一个地址，有账号倒计时结束、进入「待改密」时会立刻收到 POST：

```json
{
  "event": "password_change.pending",
  "at": 1735200000,
  "data": {
    "id": "任务ID",
    "username": "steam_user_01",
    "game": "Counter-Strike 2",
    "reason": "使用时间已用完（360 分钟）"
  }
}
```

事件类型：`password_change.pending`、`password_change.completed`、`test`。
填了签名密钥的话会带 `X-Vault-Signature: sha256=<hex>`，对**原始请求体**做 HMAC-SHA256。

> **关于 Steam 改密的现实约束**
>
> Steam 修改密码必须走官网流程，并且大概率需要邮箱验证码或 Steam Guard 动态码。
> 所以本工具负责「判定时机 → 下发任务 → 收下新密码 → 加密存回 → 状态回归可用」，
> 中间那步验证交给你的自动化程序（浏览器自动化 + 读邮箱 / 读手机令牌）。
>
> 这样既不会绕过 Steam 的安全机制（绕过会直接触发风控），也不会因为 Steam 页面改版
> 就让整个工具失效——只有那一小段自动化需要跟着改。

## 五、安全设计

- **主密码不落盘**：scrypt（N=32768, r=8, p=1）派生 32 字节密钥，只在内存中；
  主密码本身和它的哈希都不写入数据库，**忘了无法找回**。
- **每条密码独立加密**：AES-256-GCM，每次独立随机 IV + 认证标签。
- **列表接口永不返回密码**：只有显式调用解密接口才返回，且每次记审计日志。
- **闲置自动锁库**：默认 30 分钟（可在设置里改，填 0 关闭）。
- **会话令牌存 sessionStorage**：关掉标签页即失效。
- **改主密码会重加密全库**：所有账号密码用新密钥重新加密，旧令牌全部作废。
- 服务只绑定 `127.0.0.1`，并做了目录穿越防护（已实测 5 种绕过手法全部 403）。

> ⚠️ 导出的 TXT / CSV / JSON 是**明文**，用完请及时删除。

## 五之二、邮箱（自动读取 Steam 验证码）

入口在顶栏 **「更多」→「邮箱（验证码来源）」**。

### 能做什么

| 功能 | 说明 |
| --- | --- |
| 添加邮箱 | 两种类型见下 |
| 测试连接 | 只验证凭据能不能用，**不落邮件** |
| 拉取邮件 | 把邮件正文（含纯文本）存进本地库 |
| 查看邮件 | 列表 + 展开看完整正文 |
| **识别验证码** | 每封邮件直接标出识别到的验证码，一眼就能核对提取逻辑对不对 |
| **账号关联邮箱** | 账号编辑器里选「验证邮件收在哪个邮箱」 |
| **worker 自动填码** | 登录遇到 Steam Guard 时自动去邮箱取码填上 |

### 两种邮箱类型

| 类型 | 适用 | 要填什么 |
| --- | --- | --- |
| **微软邮箱** | Outlook / Hotmail / Live | `client_id` + `refresh token` |
| **取件接口** | **iCloud** 等没有公开 API 的邮箱 | 一条能返回邮件的接口地址 |

#### 为什么 iCloud 走「取件接口」

**iCloud 没有公开的邮件 API。** 苹果不为第三方提供邮件 REST 接口，
程序化访问只能走 IMAP，而 IMAP 需要 App 专用密码（`xxxx-xxxx-xxxx-xxxx`）。

如果你手上是那种「一个网址就能换回邮件」的服务（形如
`https://api.xxx.com/m?f=json&e=邮箱:密码`），那它就是**你凭据的中间人** ——
它在自己服务器上替你收信，再把结果返回给你。

**这个功能让你自己去请求那个接口，凭据不出本机。**

#### 怎么加一个 iCloud 邮箱

1. 顶栏「更多」→「邮箱」→「添加邮箱」
2. 邮箱类型选 **取件接口**
3. 把那条接口地址整条粘进去
   - **邮箱地址会从地址里自动认出来**（`?e=邮箱:密码` 这种格式）
   - 认不出来就手动填
4. 保存时会自动测一次

#### 直接粘一整行（需求里给的格式）

需求文档里给的就是一整行：

```
humbugs_errors4z@icloud.com----https://api.wdmail.top/m?f=html&e=humbugs_errors4z@icloud.com:TF4Tqxn8
```

**这一行现在可以直接粘**——粘到「取件接口地址」或「邮箱地址」任意一栏，
界面会自动按 `----` 拆成两栏（分隔符兼容 `----` / `——` / `––`）。
后端也做了一样的容错，所以直接用 API 提交这一行同样能建库。

> ⚠️ **接口地址本身就是钥匙。**
> 它把凭据写在 URL 里，**谁看到谁就能读那个邮箱的全部邮件**。
> 账号管理器会把它加密存库、接口永不返回，但**别在别处贴**。
> 界面里会明确提示这一点。

### 接口返回的字段名不认识怎么办

不知道对方怎么命名，所以解析写得**很皮实**：

| 层 | 做法 |
| --- | --- |
| ① 字段名猜测 | `subject`/`title`、`from`/`sender`、`body`/`content`… 常见命名都试一遍 |
| ② 全字符串兜底 | 把响应里**所有字符串值**（不含键名）拼起来直接抠码 |
| ③ 原文兜底 | 结构化邮件解析不出来时，把整段响应文本丢给提取器 |

**实测能扛住完全陌生的字段名**（`title` / `sender` / `content` / `ts` / `msg_id`）。

#### ⚠️ 接口通常只给最近 24 小时

实测的接口返回 `mail_query_hours: 24`，而且**改不了**。含义：

- 验证码是实时到的，**够用**
- 但**不能回溯历史** —— 拿不到 24 小时前的邮件

### 怎么用

1. 顶栏「更多」→「邮箱」→「添加邮箱」，按上面的类型填
2. 点「拉取邮件」→「查看邮件」，确认能收到信
3. **在账号里关联邮箱**：编辑账号 →「验证邮件收在哪个邮箱」
   - 同时把「邮箱」填成该账号自己的收件地址 —— **取码时靠它精确定位**
4. 之后 worker 登录遇到验证码就会自动取码填入

### 验证码是怎么认出来的

Steam 的邮箱安全码是 **5 位大写字母 + 数字**。邮件版式中英文都变过，所以用**分层兜底**：

| 层 | 做法 |
| --- | --- |
| ① 关键词锚定 | 「安全代码 / 验证码 / 代码是」附近的 5 位串 |
| ② 反向锚定 | 5 位串后面跟着「是您的 / 安全代码」之类 |
| ③ 宽松锚定 | 只靠「代码」二字（精度由校验函数兜住） |
| ④ 全文唯一候选 | 只有一个像验证码的 5 位串时采用 |
| ⑤ **多个候选 → 不给** | **绝不猜** |

> ★ 第 ⑤ 条是刻意的 ★ 猜错验证码的代价是登录失败甚至触发风控，比"没拿到"更糟。

校验函数（`looksLikeCode`）会排除 `STEAM` `HTTPS` `NOREPLY` 这类普通单词；
命中 Steam 专用字符表（`23456789BCDFGHJKMNPQRTVWXY`，去掉了 `0/O/1/I` 和全部元音）的候选置信度最高。

**拿真实邮件核对**：邮件面板里每封 Steam 邮件都会标出识别结果 ——
显示绿底验证码说明认对了，显示「没识别出验证码」就点开看正文，把实际格式发我调正则。

### worker 的自动取码

登录时如果出现验证码输入框，worker 会：

```
检测到验证码输入框 → 让服务端去邮箱取码（服务端自己轮询，间隔递增）
  ├─ 取到 → 填入 → 提交 → 继续
  └─ 取不到 → 打印「请手动输入」→ 继续等你自己填（人工永远是兜底）
```

**只尝试一次，不会反复轰炸邮箱。** 相关配置（worker 的 `.env`）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `AUTO_CODE` | `true` | 填 `false` 一律手动 |
| `CODE_WAIT_SEC` | `90` | 让服务端在邮箱里最多轮询多少秒 |
| `LOGIN_TIMEOUT_MS` | `180000` | 登录阶段最多等多久（要留够人工输码的时间） |

## 五之三、邮箱相关的安全

- **refresh token 用 AES-256-GCM 加密存库**，和账号密码同一套密钥
- **接口永不返回 token**，只返回 `hasToken` 布尔值和一个截断的 client_id 提示
- **审计日志里也没有 token 明文**
- ⚠️ **建议用专用邮箱** —— refresh token 能读取该邮箱的**全部**邮件，
  权限远大于单个 Steam 账号。别把主邮箱的 token 放进来

### 防封设计（这是重点）

微软对自动化访问的检测是主动的。所以这一层的设计原则是**尽量不像机器人**：

| 措施 | 默认值 | 作用 |
| --- | --- | --- |
| 全局串行 | 强制 | 同一时刻只发一个请求 |
| 最小间隔 | 1500ms | 两次请求之间至少隔这么久 |
| 随机抖动 | 0~800ms | 叠加随机量，避免"精确每 1500ms 一次"这种特征 |
| 限流退避 | 最多重试 3 次 | 收 429 时读 `Retry-After`，并叠加指数退避 |
| 增量拉取 | 开 | 只取上次之后到达的邮件，不反复全量拉 |
| 手动触发 | 开 | 不做后台高频轮询 |
| 取码轮询递增 | 10s → 14s → 18s… 封顶 30s | 等待时也不会把请求打得太密 |

**改这些参数**（可选，一般不用动）：

```bash
MAIL_MIN_INTERVAL_MS=1500   # 最小请求间隔
MAIL_JITTER_MS=800          # 随机抖动上限
MAIL_MAX_RETRIES=3          # 可重试错误的重试次数
MAIL_FETCH_TOP=20           # 单次最多拉多少封
```

### 令牌是怎么维护的

| Token | 寿命 | 处理 |
| --- | --- | --- |
| access token | 约 1 小时 | 内存缓存，过期前自动用 refresh token 换 |
| refresh token | 90 天滑动窗口 | **每次刷新后回写**（见下） |

> **★ 微软会轮换 refresh token ★**
> 每次刷新可能返回一个新的，旧的随之作废。所以每次刷新后都必须回写数据库 ——
> 不回写的话，跑一段时间后所有 token 会集体失效。
> 这个行为有专门的测试守着（`npm run test:mail`）。

**怎么判断 token 挂了**：邮箱卡片上的状态会变成 **「需重新授权」**，并显示具体原因
（比如 `AADSTS700082: refresh token 因长期未使用而过期`）。
这时需要重新获取 token 并编辑该邮箱。

> ⚠️ 邮箱取码失败时接口返回 **400 + `code: 'need_reauth'`**，**故意不用 401**。
> 因为前端的 `api.js` 对 401 的处理是「锁库、踢回解锁页」——那是给保险库会话用的。
> 混用会导致「某个邮箱 token 过期」变成「整个保险库被锁上」。测试里有专门的断言守着这条。

## 八、常见问题

**忘记主密码了怎么办？**
无法找回。这是刻意的设计。只能重新建库，把账号重新录一遍。

**账号一直卡在「使用中」？**
服务端每 5 秒会推进一次状态。如果卡住，多半是电脑休眠导致服务被挂起，
重启服务即可；服务重启时会自动把状态与会话对齐。

**改密任务一直没人处理？**
说明还没有自动化程序来接。任务会一直等着，不会过期。
可以在卡片菜单里点「跳过改密放回可用」，或者手动改完密码填回来。

**想让账号尽快进入「待改密」测试流程？**
添加账号时把「使用时间」设成 1 分钟，点开始使用，等 1 分钟即可看到完整流转。

**端口 8787 被占用了？**
命令行里执行 `set PORT=9000 && npm start`。

**账号能在两个界面同时出现吗？**
不能。状态由服务端 `accounts.state` 唯一持有，且自检里有一条断言专门验证
「三态计数相加 == 总数」，确保不会重复归属。

**升级后界面没变化？**
前端资源构建完就生效了，服务端是按请求现读 `web/dist` 的，不用重启服务。
浏览器可能缓存了旧的 `index.html`，按 `Ctrl + F5` 强制刷新一次即可。

**worker 改完密码，界面会自动更新吗？**
会。前端每 8 秒向服务端对齐一次，切回标签页时还会立刻再同步一次 ——
**不需要手动刷新**。

> 之前这里有个坑：同步前会判断「标签页是否在前台」，在后台就跳过。
> 结果用 worker 改密时（你正看着 worker 打开的浏览器窗口，管理器的标签页就在后台），
> 一次都不同步，改完必须手动刷新才看得到。已修掉。

**「待改密」里没有账号，worker 却一直登录某个空闲账号？**

那是**僵尸任务**：账号已经回到「可用」，但改密任务还挂在队列里，worker 每次轮询都重新认领它。

根因是"账号回到可用"的路径不止一条（跳过改密 / 手动改密 / AI 完成 / 直接删号），
早期只有 `setPassword` 记得关任务，`skipChange` 忘了。

现在有**三道闸**一起挡：

| 闸 | 位置 | 作用 |
| --- | --- | --- |
| ① 回到可用时自动关任务 | `_resolveToAvailable` | 所有回头路都覆盖到 |
| ② 重试前检查账号状态 | `failTask` | 账号已不在待改密 → 任务终止，不再入队 |
| ③ 认领前检查账号状态 | `claimTask` | 不满足就 409 拒绝并把任务作废 |
| ④ **定时对账** | 调度器每 5 秒 `reconcileTasks()` | 清掉任何残留的僵尸任务 |

> 第 ④ 条是兜底：与其在每条路径上逐个堵，不如让**不变量自我修复** ——
> 服务端是任务状态的唯一权威。
> `scripts/selftest.mjs` 的 `[11]` 节专门守着这条。

**为什么卡片不用毛玻璃了？**刻意的。一屏可能有几十张卡片，而它们全都躺在滑动容器这一个合成层里；
几十个 `backdrop-filter` 模糊层叠加会让 Chromium 渲染不出来（表现为卡片
"看不见、点一下才出现"）。改成半透明底色后观感几乎一致，但稳定且快很多。
同理，所有入场动画都不再使用 `animation-fill-mode: both` —— 那会让动画
在未执行时把元素停在 `opacity: 0`，也就是"数据在、DOM 在，但肉眼看不见"。

**顶栏为什么写了 `position: relative; z-index: 80`？**

**别删这两行。** `.topbar` 上有 `backdrop-filter`，它会创建**层叠上下文**。
「更多」菜单在它里面，菜单自己的 `z-index: 60` 只在这个上下文**内部**有效 ——
对 DOM 里更靠后的 `.pager`（`position: relative`）完全无效。

后果是菜单下半部分被 pager 盖住，**「设置 / 切换主题 / 锁定保险库」点不到**
（实测 6 项里 4 项被盖）。把顶栏整体提到 80 就解决了：
高于 pager 和卡片菜单(40)，低于弹窗(100)与 toast(300)。

`worker/test-ui.mjs` 会用 `elementFromPoint` 实测每一项有没有被盖住，
**并且把三个功能真点一遍** —— 正是为了防止这个坑被改回去。

## 十、本轮修复记录（对着需求逐条核过一遍）

拿需求文档逐条对照实现后，发现并修掉了这些问题（每条都有回归测试守着）：

| # | 问题 | 现象 | 修法 |
| --- | --- | --- | --- |
| 1 | **点击标签不换页** | 标签高亮了，下面的内容还停在上一个界面 | `SwipePager` 的 `targetIndex` 是普通变量不是 `ref`，`computed` 收集不到依赖不会重算 |
| 2 | **批量导入丢字段** | `账号--密码--邮箱--游戏名` 只吃进前两段，邮箱和游戏名被静默吞掉 | `parseBulkText` 支持 2~4 段，第 3 段带 `@` 当邮箱、否则当游戏名 |
| 3 | **整行邮箱粘不进去** | 需求里那条 `邮箱----取件地址` 必须手工拆成两栏，整行粘会报错 | 新增 `splitMailboxPaste()`，前后端同时容错 |
| 4 | **卡住时的现场文件会被覆盖** | 两次 dump 写同一套文件名，第二次（标签写着"登录阶段卡住"）把真现场盖掉 | 一次 dump，说明按当前页面实测判断 |
| 5 | **六大步骤没有"开始"日志** | 卡在某一步时日志最后一行还停在上一行，看不出进没进这一步 | `step()` 开始/结束/失败各打一行（带耗时）；逐字符输入也打点（只打长度，不打内容） |
| 6 | **卡片菜单会被裁掉** | 列表底部的卡片，菜单超出滚动容器后被裁，按钮点不到 | 下方空间不够时菜单自动向上弹（`.menu--up`） |
| 7 | **今日次数口径只有一个** | 需求要的是"改密次数"，界面只有"开始使用次数" | 两个口径都给：`todaySessions` + `todayChanges` |
| 8 | **`/api/stats/today` 用 UTC 日界** | 东八区早上 8 点前返回的还是"昨天"，和库里的本地 `day_key` 对不上 | 统一走本地 `dayKey()` |
| 9 | **外部程序无法取号** | 「开始使用 → 输出账号/密码」只有会话鉴权，别的程序调不动 | 新增 3 个 `X-API-Key` 接口（见第四节） |
| 10 | **一级导航写死 3 列** | 「添加账号」不在导航里，加界面要改三个文件 | 导航数据化：`TABS` + `ADD_SCREEN` + `ATTACHED_SCREENS` |
| 11 | **密码测试随机失败** | 一致性测试偶尔报"数字类不均匀"（实测 28 次里错 1 次） | χ² 上限公式 `df*2.1+3` 在 df=9 时比真值还严（21.9 < 27.9），改用真实的 0.001 上尾临界值 |
